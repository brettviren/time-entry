#+title: time-entry

Monthly time allocator for fiscal-year project reporting, with (semi-)automated
entry into the Workday time-entry calendar.

Given a set of projects with target percentages, =time-entry= allocates each
month's working days to projects using a Hamilton (largest-remainder) method
that compensates for cumulative drift across the fiscal year (which ends Sep
30).  It can then read the current state of the Workday calendar, diff it
against the plan and drive a browser to enter the missing days.

* Install

As an end-user:
#+begin_example
uv tool install git+https://github.com/brettviren/time-entry
uv tool upgrade time-entry
#+end_example

As a developer:
#+begin_example
git clone git@github.com:brettviren/time-entry.git
cd time-entry
uv tool install -e .
uv run pytest
#+end_example

The =login=, =get=, =diff=, =apply=, =submit= and =workflow= commands drive a
real browser via Playwright.  Its Chromium must be installed once:

#+begin_example
time-entry install-browser
#+end_example

This uses the exact Playwright version bundled with =time-entry=.  Do not use
an unrelated system =playwright= command, which may download an incompatible
Chromium revision.

* Basic use

#+begin_example
time-entry --help
time-entry <command> --help
#+end_example

The typical monthly workflow:

#+begin_example
time-entry login         # opens a browser for SSO+2FA, saves the session
time-entry plan          # compute and save this month's allocation
time-entry get           # read what Workday currently holds
time-entry diff          # plan vs Workday, saved as a diff JSON
time-entry apply         # dry-run of the diff
time-entry apply --yes   # enter and save the days; does not submit
time-entry submit        # dry-run: show which month's timecard would submit
time-entry submit --yes  # review, then submit the timecard
#+end_example

The individual =get=, =diff=, =apply= and =submit= commands run Chromium
headlessly by default.  Put the top-level =--headed= option before the command
to show the browser, for example:

#+begin_example
time-entry --headed get
time-entry --headed apply --yes
#+end_example

=workflow= is the exception: it remains headed by default and accepts
=--headless= as an opt-in for its post-login browser steps.  Because
inspection requires visual interaction, invoke it as =time-entry --headed
apply --inspect=.

=login= supports two modes, selected by =mode= in the config's =[login]=
section (the default) and overridable per run with =time-entry login
--headed= / =--headless=:

- =headed= — opens a visible browser; you complete SSO and DUO manually.
- =headless= — the script clicks through the "BNL" organization picker on the
  tenant page and fills the SSO form itself; you only approve the
  DUO push on your device. It skips Workday's post-DUO "Remember Device?"
  prompt and saves the session only after the authenticated Workday shell
  loads. Requires =username= in =[login]=. By default, the password is prompted
  in the terminal with input hidden.

To retrieve the password from a password manager, configure a command:

#+begin_src toml
[login]
mode = "headless"
username = "jdoe"
password_command = "pass gov/bnl/domain"
#+end_src

Or override it for one invocation (also supported with =workflow=):

#+begin_example
time-entry --password-command=time-entry-pass.sh login --headless
#+end_example

The command runs only for headless login. Its first stdout line is the
password; later lines are ignored, and password spaces are preserved.
Commands support quoted arguments and use PATH lookup, without shell
expansion or pipelines. For shell operations, use an executable script
with a shebang (for example, =#!/bin/sh=), or pass an explicit shell. A
script may run =pass gov/bnl/domain | head -1=; invoking =pass= directly
avoids needing that pipeline. Failed commands and empty passwords abort
login without printing command output. Omit =password_command= to use
the terminal prompt. The old plaintext =[login] password= option is
rejected: remove it from existing config files.

As a shortcut for the full sequence, use:

#+begin_example
time-entry workflow
time-entry --headless workflow  # only a headed login opens a visible window
#+end_example

This runs =login=, =get=, =plan= and =diff=.  If changes remain, it asks =Do you
want to apply this?= once, then repeats =apply= and =diff= until the diff is
clean, with a maximum of three apply attempts.  Each attempt prints its number.
If changes remain after the third attempt, the command exits with an error and
does not offer submission.  Only after a clean diff does it ask =Do you want to
submit this?=; submission remains optional and defaults to no.  The optional
=YYYY-MM= argument selects a month.  =--dry-run= is not supported by =workflow=;
use the individual commands for a partial or preview run.

Month-oriented commands take an optional =YYYY-MM= argument and default to the
current month.  Also useful:

#+begin_example
time-entry init          # write a template config
time-entry show          # display a saved month
time-entry status        # FY-to-date totals vs targets
#+end_example

* Files

Configuration lives in =$XDG_CONFIG_HOME/time-entry/= (=~/.config/time-entry/=
by default):

- =config.toml= :: fiscal year, =days_off=, Workday URLs and the =[[projects]]=
  entries (code, pct, desc).  Percentages must sum to 100.  Run =time-entry
  init= to write a template.

State lives in =$XDG_STATE_HOME/time-entry/=.  Note that when =XDG_STATE_HOME=
is unset, state falls back to =~/.config/time-entry/= (not =~/.local/state/=),
which is where existing state may be found:

- =time-entry.json= :: saved monthly plans/records.
- =time-entry-auth.json= :: the Playwright =storage_state= saved by =login=.
- =time-entry-diff-YYYY-MM.json= :: the todo list written by =diff= and consumed
  by =apply=.
- =workday_*.html= :: page captures for debugging selectors, safe to delete.

The config, records and auth-state paths can be overridden with top-level
options.  Diff JSON and debug captures always use the state directory; see
=time-entry --help=.

* Cautions and caveats

Workday's DOM is tenant- and version-specific.  The selectors here were
confirmed against BNL's tenant and drift over time.  To be most cautious, run
=apply= without =--yes= first, re-run =diff= after =apply --yes= to confirm what
landed, and only then run =submit --yes=.  Submission is never performed by
=apply=.

Headless =login= and =submit= have been exercised successfully against the live
BNL tenant.  Workday's DOM remains version-specific, so verify the resulting
status manually after future Workday updates.  The combined =workflow= command
still has automated coverage only.

The current policy fills in the month using 8 hour per day atoms so that it is accurate on average compared to the configured %FTE per project.  The current policy has no facility to make individual hours/days record what effort was actually done those specific hours/days.  That is, the configured %FTE per project is taken as ground truth for the month as a whole.
